# QA Check CLI 2.0.0 — Proposed release notes

Status: prepared for maintainer review; not published. Release date is unassigned.

QA Check CLI 2.0.0 brings the Lighthouse 13.5 migration and dependency security
remediation to the CLI package. The major version marks removal of Node 20 support.

## Upgrade requirements

Use Node.js >=22.19 before installing or running v2. Validated migration targets
are Node 22.19+ and Node 24 on Windows, Ubuntu and macOS. Earlier runtimes are
rejected before the application loads, with the required version in the error.

Update local environments, containers and CI runners first. Use Node 22.19.0 or a
validated Node 24 runtime in actions/setup-node. Fresh `qa-check init` output uses
Node 22.19.0; existing generated workflows are not overwritten and must be updated
by their owners. The current npm engine policy may warn during an ordinary install;
use `--engine-strict` when installation must enforce compatibility. Runtime rejection
is always enforced. Remaining on the older Node 20-compatible dependency tree does
not resolve its known dependency security findings.

## Lighthouse and report compatibility

The Lighthouse range is ^13.5.0, with 13.5.0 resolved in the source lockfile. A fresh
consumer resolves its own compatible dependency tree; source and consumer are
audited separately. Browser selection, CDP readiness, bounded timeouts and owned
Chrome/worker cleanup remain enforced. Failed or incomplete audits cannot become
successful full-confidence evidence.

The QA Check score calculation and gate policy are unchanged. Lighthouse's own
accessibility/best-practices audits and category weights differ from 12.x, so raw
reports and scores are not promised to be identical across engines. Compare
representative pages, review differences and explicitly approve any new baseline.
No baseline is automatically refreshed by this release preparation.

Existing `metrics.TTFB` continues to mean server-response duration, using the new
document latency insight when needed and supporting the legacy audit. Insight
savings are not substituted for timing. `navigationTTFB` records navigation-to-first-
byte separately; engine version and metric provenance are additive evidence.
Unavailable metrics remain absent rather than fabricated as zero.

The executable remains `qa-check`, the package is ESM, and HTML, JSON, Markdown and
PDF reports remain supported. No supported programmatic library API or exports map
is introduced. Existing command syntax and configured regression checks remain.

## Security remediation

The earlier fast-glob/micromatch/braces cohort was replaced with tinyglobby.
Lighthouse 13.5 upgrades its browser-management and telemetry cohorts, removing
affected archive, FTP and proxy paths. This removes vulnerable dependencies rather
than hiding their audit findings. No forced audit fixes, unreviewed overrides,
allowlist exceptions or lower security thresholds are part of this release.

See [release readiness](../v2-release-readiness.md) for the current full-package source and installed
consumer audit counts, validation evidence and limitations. An audit is a dated
advisory check, not a guarantee that a package has no security defects.

## Packaging and validation

Normal `npm pack` runs the build through `prepack`. Clean release preparation still
starts with npm ci and full validation. The packed allowlist remains bin/dist plus
npm's root package, README and license files; tests, reports, caches and application
fixtures are excluded. Release notes and changelog are repository documents.

The maintainer must approve the diff and the proposed package version, validate
the final approved commit in hosted CI, and authorize any later release operation
separately. This preparation does not commit, push, tag, merge or publish.
